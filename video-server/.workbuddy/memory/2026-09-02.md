## 环境备注
- **沙箱会回收跨调用启动的进程**：PowerShell/Bash 工具调用里 `start` 拉起的进程会在调用结束后
  若干分钟内被清掉。要在调用间隔里做 HTTP 验证，必须**在同一次 Bash 调用内**起进程 + 发请求。
- PowerShell 工具**禁止** `cmd.exe` 和 `[Diagnostics.Process]::Start`；且原生命令写 stderr 会让
  PowerShell 报 exit 1（假象），所以要判脚本真实退出码，用一个 wrapper .bat（
  `call 目标.bat %*` 后 `echo EXITCODE=%errorlevel%`）最可靠。
- 一次 PowerShell 调用里连续 `&` 跑两个 .bat 时，**第二个常不执行**（前一个非零退出即中断）。
  分成两次调用。
- `rm -f` 批量删文件偶发 SIGTERM（部分删除成功）；改用 PowerShell `Remove-Item -LiteralPath` 逐个删。
- PowerShell `>` 落盘是 **UTF-16**，用 `python -c "...decode('utf-16')"` 读。
- 服务被回收后 `localhost:8081` 会返回 **502 `upstream connect failed`**（沙箱代理），
  不要误判成应用故障；用 `tasklist` 或直接重启确认。

## WebRTC 通、HLS 两端黑屏：根因检测（已实测）

### 现象
用户实测：WebRTC 在主机 + 手机都出画；HLS（点按钮 / WebRTC 超时兜底）两端都黑屏。

### 检测过程（同一次 Bash 调用内起服务 + agent 再抓 HLS）
- `GET /hls/camera01/index.m3u8`（代理 :8081） → **200** 合法 `#EXTM3U` 顶层清单
- 媒体清单 → **200**，但内容是 **LL-HLS**：`#EXT-X-SERVER-CONTROL` / `#EXT-X-PART-INF` /
  `#EXT-X-MAP` + 大量 `#EXT-X-GAP` 占位段 `gap.mp4`
- `*_init.mp4` 经代理 → **200 `video/mp4` 682B**（合法 fmp4 init）
- `gap.mp4` 占位段经代理 → **200 `text/html` ~6.8KB**（MediaMTX 的错误页，非视频）

### 根因
`internal/mediamtx/manager.go` 的 `GenerateConfig()` 写了 `hls: true` 但**没钉 `hlsVariant`**
→ MediaMTX v1.20.1 默认 `hlsVariant: lowLatency`（LL-HLS/fmp4）。
- LL-HLS 清单 gap 段以 `text/html` 返回 → hls.js（`lowLatencyMode: true`）拿到非视频 MIME →
  **致命错误** → `scheduleHLSRetry` 死循环 → 黑屏。
- 代理层本身没问题（index/媒体/init 都 200），故障在浏览器端解析 LL-HLS 的 GAP/HTML。
- 违背设计意图：代码注释明确"HLS 是手机兜底路"，兜底必须最稳，而 LL-HLS/fmp4 最脆。

### 修复（一行，尚未应用，待用户确认）
在 `GenerateConfig()` 格式化串 `hls: true` / `hlsAddress: %s` 后加 `hlsVariant: mpegts`。
经典 MPEG-TS HLS：hls.js 默认支持、iOS Safari 原生支持，无 LL-HLS 会话脆弱性。
（静态 `mediamtx/mediamtx.yml` 里的 `hlsVariant: lowLatency` 是误导，运行时根本不读它。）

### 验证命令

## 硬化 `scripts/verify_e2e.py` 合成回归门（已闭环，PASS=11）

上一轮 e2e 报 `cameras auto-registered` FAIL（/api/cameras 返回 null）。本以为只是沙箱回收假象，
实跑（前台、同进程内 server 全程存活）后发现**真因：ffmpeg 推流根本没连上 mediamtx**，监控器
自然无 camera 可登记。逐层定位：

### 根因（关键坑）
- e2e 用 `rtsp://localhost:<port>/camera01` 推流。本机 `localhost` 优先解析到 **::1 (IPv6)**，
  而 **MediaMTX 的 RTSP 监听器是 IPv4-only**（`0.0.0.0:<port>`，日志可见；HTTP 服务是双栈所以
  /api/health 能过，但 RTSP 不行）。ffmpeg 连 ::1 失败且不回退 127.0.0.1 → mediamtx `paths/list`
  始终 0 path → 监控器跳过 → /api/cameras = null。

## 二轮：HLS 网页"仍黑屏"真因 = 前端是 go:embed 进二进制（旧笔记误判为磁盘直出）

用户反馈：后端改 `hlsVariant: mpegts` 后 HLS 网页**仍黑屏**。逐层排查后定位真因，与后端/lowLatencyMode 无关。

### 真因
- `web/embed.go` 有 `//go:embed all:dist`，`server.go:50` 用 `fs.Sub(webstatic.Dist,"dist")` 提供 SPA
  —— **Web UI 是编译进二进制的，不是磁盘直出**（MEMORY.md 与上面第 19-20 行旧笔记"无 go:embed"是错的）。
- 上一轮只改了 Go（`hlsVariant: mpegts`）并 `go build`，但**没 `npm run build`**，所以运行中的二进制
  从没包含任何 Web UI 改动 → 前端停在旧状态（仍 `lowLatencyMode:true`），网页纹丝不动。
- 注：即便旧前端 `lowLatencyMode:true` 配经典 mpegts，hls.js 对经典 playlist 是 no-op（源 `base-playlist-controller`
  的 LL 逻辑被 `canBlockReload && advanced` 门控），本应可播；所以"仍黑"最终是**运行中二进制未含任何修复**
  （既没 mpegts 后端、也没新前端）所致——必须 `npm run build` + `go build` + 重启才生效。

### 前端对齐修复（web/src/webrtc/player.ts）
- `startHLS()` 的 `new Hls({ enableWorker:true, lowLatencyMode:true })` → `lowLatencyMode:false`
  （后端是经典 mpegts，不是 LL-HLS；lowLatencyMode 是 LL-HLS 专有客户端特性，对经典流是错配）。
- 加健壮性：`fragLoadingMaxRetry/manifestLoadingMaxRetry/levelLoadingMaxRetry = 6`；
  ERROR 处理对 `NETWORK_ERROR` 调 `hls.startLoad()`、`MEDIA_ERROR` 调 `hls.recoverMediaError()` 自愈，

### 三轮：HLS 网页仍黑屏的**真因** = WebRTC→HLS 切换残留 `video.srcObject`（13:00-14:00）
- **背景**：上轮 embed 重建是必要非充分；用户重启新二进制+硬刷新后仍黑 → 存在独立前端 bug。
- **定位方法**（Playwright，服务+ffmpeg+Chromium 同进程）：
  1) 同源页注入 hls.js 直连代理 → 出画（320×240、ct 推进）→ 后端/代理正常；
  2) 真实 App 路由 `/`→点卡片→点 HLS 按钮 → 只拉播放列表、零 `.ts`、元素 2×2、ct 卡 0 → 复现黑屏；
  3) 同流程先 `video.srcObject=null` 再点 HLS → 立刻出画 → 锁定 srcObject 冲突；
  4) 翻转 `enableWorker`（隔离测试 true 照样出画）→ 排除 Worker 假设。
- **真因**：播放器先走 WebRTC，`ontrack` 把 `MediaStream` 塞进 `video.srcObject`；切 HLS 时
  `teardownPeer()` 只 `pc.close()` **没清 `srcObject`** → `hls.attachMedia(video)` 想用 `src` 接管，
  但 **`srcObject` 优先级高于 `src`** → hls.js 拉到的 `.ts` 永远渲染不出 → 黑屏（2×2 占位、ct=0）。
  curl 测不出（代理层 `.ts` 200 video/mp2t 全绿）、浏览器必踩。
- **修复（`web/src/webrtc/player.ts`）**：①`teardownPeer()` close 后 `srcObject=null`；
  ②`startHLS()` 开头 `srcObject=null`（hls 接管前清场）；③`teardownHLS()`/`connectWebRTC()` 开头
  `removeAttribute('src')`+`load()`+`srcObject=null`（双向切换都从干净 `<video>` 开始）。
- **重建**：`npm run build`（产 `index-BsYIT4ll.js`）→ `go build -trimpath -o video-server.exe`（13:57:51）。
  `grep BsYIT4ll video-server.exe` 命中。
- **验证（真实 App 流程，无手动补丁）**：点 HLS 后 `.ts` 200 video/mp2t、元素 320×240、
  `currentTime` 0.04→14.04s、`paused=false` → **出画，黑屏消除**。`bufferStalledError` 仅为
  headless 合成源偏慢的非致命告警。
- **铁律**：WebRTC 与 HLS 共用同一 `<video>` 时，切传输必须清 `srcObject` 与 `src`（srcObject 优先于 src）。
- 已同步：MEMORY.md 新增三轮章节；skill `soc-video-streaming`（系统级+项目级）新增"二次坑"小节；

### 四轮：HLS 时延 5-6s → 前端 live 参数调优（14:15-14:50）
