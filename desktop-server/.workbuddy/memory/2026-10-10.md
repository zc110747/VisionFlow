## ⚠ 关键坑：FFmpeg.AutoGen 与 ffmpeg 运行库必须主版本严格对齐

**症状**：调用任何 `av_*`（如 `av_version_info()`）抛
`NotSupportedException: Specified method is not supported.`——完全看不出跟版本有关。

**根因**：AutoGen 用**编译期常量** `LIBAVUTIL_VERSION_MAJOR` 等拼 DLL 名去加载
（找的是 `avutil-60.dll` 这种带主版本的固定名）。包版本与本机运行库主版本
差 1 就全部加载失败。

**排查手法**（反射读 AutoGen 内部常量，一行定死）：
```csharp
typeof(ffmpeg).GetField("LIBAVUTIL_VERSION_MAJOR",
    BindingFlags.Public|BindingFlags.NonPublic|BindingFlags.Static)?.GetValue(null)
```
与目录里实际 DLL 名的主版本号对比即可。

**版本对应表**：

| FFmpeg | avutil | avcodec | avformat | avfilter | swscale | swresample |
|---|---|---|---|---|---|---|
| 8.0 / **8.1** | **60** | **62** | **62** | **11** | **9** | **6** |
| 9.0 / master | 61 | 63 | 63 | 12 | 10 | 7 |
| 7.1 | 59 | 61 | 61 | 10 | 8 | 5 |

**本项目锁定**：`FFmpeg.AutoGen 8.0.0` + `ffmpeg-n8.1-latest-win64-gpl-shared`
（路径 `D:\data\agent-tools\ffmpeg-n8.1-latest-win64-gpl-shared`，可用环境变量
`FFMPEG_ROOT` 覆盖）。

**注意本机另有一份 `ffmpeg-master-latest-win64-gpl-shared`**（avutil-61/avcodec-63，
即 9.0 系）——与 AutoGen 8.0.0 不兼容，不要误用。

## 其它已踩的坑

1. **`DllImport` + `ExactSpelling=true` + `CharSet.Unicode`** → 运行时找的是不带
   `W` 后缀的导出名，kernel32 会报 "Unable to find an entry point named
   'SetDllDirectory'"。去掉 `ExactSpelling` 让 marshaler 自动配 `W` 后缀。
2. **`LibraryImport` 源生成器** 解析 `SetDllDirectory` 同样失败，改用经典
   `DllImport`。
3. **.NET 9 WinForms 禁止在 manifest 写 `dpiAware`**（error `WFO0003`），
   必须走项目属性 `<ApplicationHighDpiMode>PerMonitorV2</ApplicationHighDpiMode>`。
4. **自定义 Control 的公开属性** 需要 `[DesignerSerializationVisibility(Hidden)]`
   + `[Browsable(false)]`，否则 error `WFO1000`。
5. **`rtsp` 是 demuxer 不是 avio 协议** —— 用 `av_find_input_format("rtsp")` 判断，
   绝不能用 `avio_enum_protocols`（那样会假失败）。
6. **`av_strerror` 在本版本没有托管重载**，只有 `(int, byte*, ulong)`，需手工开缓冲。

### ⚠ 重要性能发现（反直觉，必须记住）

**当前架构下硬解是净负优化**，4K H264 实测：

| 环节 | 硬解 | 软解 |
|---|---|---|
| 解码 | **0.97 ms/帧** | 5.89 ms/帧 |
| hwframe 搬运 | 10.14 ms/帧 | — |
| sws 转 BGRA | 14.80 ms/帧 | 8.02 ms/帧 |
| **合计** | **25.9 ms/帧** | **13.9 ms/帧** |

- 解码环节硬解快 **6.1×**，机制完全正确
- 但 `av_hwframe_transfer_data`（显存→内存）+ 更贵的 sws 把收益吃光
- **根本矛盾**：GDI+ 只能吃系统内存位图，所以"解码在 GPU"的优势被"必须搬回 CPU"抵消

**已实测排除的优化方向**（不要再试）：
- 换 sws 算法：BILINEAR/FAST_BILINEAR/POINT 差异 <3%
- 给 sws 开多线程：threads=2/4/12 几乎无差异
- 判定：`sws_scale` 同尺寸转换是**内存带宽受限**，4K 单帧 33MB 读写 = 66MB 流量，
  ~6.2 GB/s 已在单通道内存带宽合理量级

**唯一根本解**：渲染层直接消费 D3D11 纹理（`D3DImage` 或子窗口托管交换链），
彻底取消 transfer + sws。需单独立项。

### ⚠ 一致性验证的结论（避免误判为 bug）

硬解与软解输出的 PNG **字节不同且 PSNR 仅 34.7dB**，容易误判为 bug。实测结论：

- **我的软解输出 vs ffmpeg CLI 基准 = PSNR ∞（逐像素完全一致）** → 证明实现无错
- 差异**只出现在高频边缘**（对角线、网格纹理），平坦色块差异为 0
- 根因：D3D11VA 的色度上采样（NV12）与软解（YUV420P）插值实现不同，属 ffmpeg 既定行为
- 判据：若是我写错（stride 错位/平面颠倒），平坦区会出现系统性色带；实测平坦区为 0

### 其它已踩的坑（阶段 2 新增）

1. **FFmpeg 解码是异步的** —— 真正解码发生在 `avcodec_send_packet`，
   `avcodec_receive_frame` 只是取帧。只计时 receive 会得到「软解 0.01ms/帧」的荒谬结果。
   计时必须把 send+receive 合并。
2. **AutoGen 8.0.0 的 `AVFrame::data/linesize` 是固定数组封装类型，索引器参数为 `uint`**，
   不是 `int`。
3. **`av_frame_get_buffer` 的 align 参数是 `int`**（不是 uint）；
   `av_opt_set_int` 的 val 是 `long`。
4. **对实例字段取址（`&_hwDeviceCtx`）需要 `fixed`** —— 封装成辅助方法避免散落。
5. **`LibraryImport` 源生成器的 `SetDllDirectory` 解析会失败**，用经典 `DllImport`；
   且**不能加 `ExactSpelling=true`**（会去找不带 W 后缀的导出名）。
6. **.bat 断言绝不能用中文关键字** —— GBK 代码页 + `for /f` 组合会产生
   "文件名、目录名或卷标语法不正确" 之类的乱码级联错误，且错误信息误导。
   改法：程序侧输出 **ASCII 的 `RESULT key=value` 行**，bat 用 `findstr` 匹配。
7. **`lib子集` 的 `sws_getCachedContext` 传相同参数会复用**，传不同参数会重建 ——
   跨分辨率切换时注意。
8. **GDI+ `Bitmap` 的 `Format32bppArgb` 内存布局 = BGRA**，与 `AV_PIX_FMT_BGRA` 直接对应，
   可 `LockBits` 后直接给 `sws_scale` 写，无需额外拷贝。

### ⚠ 本轮最大的坑：MF GUID 凭印象写全是错的，且失败完全静默

**症状**：`MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING` 设成 `true`
返回 `S_OK`，但 `SetCurrentMediaType` 请求 RGB32 一律 `MF_E_INVALIDMEDIATYPE`，
连读 121 次拿不到一帧。

**根因**：我写的 GUID 是**凭空编造**的（`BF12BEED-...`）。
`IMFAttributes::SetGUID` 对**未知键返回 S_OK 但不生效** —— 于是
SourceReader 静默地不插入 Video Processor MFT，NV12/MJPEG 无法转 RGB32。

**正确值**（对照 `C:\Program Files (x86)\Windows Kits\10\Include\<ver>\um\mfreadwrite.h`）：
```csharp
// MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING
new("0F81DA2C-B537-4672-A8B2-A681B17307A3")
// MF_MT_FRAME_RATE
new("c459a2e8-3d2c-4e44-b132-fee5156c7bb0")
// MFVideoFormat_RGB32
new("00000016-0000-0010-8000-00AA00389B71")
// MFVideoFormat_NV12
new("3231564E-0000-0010-8000-00AA00389B71")
```

**陷阱**：`mfreadwrite.h` 里 `MF_MT_FRAME_RATE` 上面一行的注释是**另一个过时 GUID**，
照注释抄会错。**必须抄代码行，不抄注释。**

**铁律**：所有 MF 属性 GUID 必须逐字对照 SDK 头文件。`SetGUID` 静默失败，
没有任何运行时反馈能帮你发现写错。

5. **MF 不会列出 PnP 里那个多余的 "UVC Control" 复合节点**（实测本机 3 个 PnP 节点

### ⚠ 关键修正：服务端 rtsp_url 的主机必须改写成回环地址

**症状**：下拉框选中网络相机 → 播放失败，`avformat_open_input` 报
`Server returned 404 Not Found`。

**根因**：服务端 `rtsp_url` 返回的是 `rtsp://192.168.16.52:8554/<path>` ——
那是**服务端那台机器的网卡地址**（它按"局域网内其它客户端访问"假设生成）。
桌面端与服务端同机运行时，这个地址一旦遇到网卡 IP 变更 / 多网卡 / DHCP 续租，
就会连不上（404）。

**修正**（`ResolvePlayUrl` + `RewriteHost`）：
只要 REST 基地址指向本机（127.0.0.1 / localhost），
就把播放地址主机**强制换成回环**——同机场景下这是唯一恒定的选择。
基地址是远程时保留服务端给出的主机。

**验证**：推一路 ffmpeg 合成流到 `cam-probe01` → 客户端改写为
`rtsp://127.0.0.1:8554/cam-probe01` → RTSP/TCP 直拉成功，
`h264 1280x720`，**D3D11VA 硬解启用**，30/30 帧 36.9fps，`verdict=PASS`。

### ⚠ 离线相机不该被默认选中

7 个测试相机**全部 offline**，且服务端按创建时间排序（最新建的排最前），
导致用户一进界面默认选中的就是死的。修法：
- `CameraDto.IsOnline`（`status == "online"`）
- 下拉框条目标注「在线/离线」
- 列表**在线优先**重排（同组内保持服务端原序）

### ⚠ 坐标双参考系（最容易错的一处）

- AI 的 bbox/keypoints 用 **`frame.video_width/height`**（原始视频像素）
- 显示用**解码位图尺寸**，且还要经 `VideoTransform` 做 Letterbox 映射
- 必须先归一化再映射，**不能直接拿原始像素当显示坐标**：
```csharp
float nx = (float)(x / refW);
float ny = (float)(y / refH);
return new PointF(
    transform.OffsetX + nx * transform.Destination.Width,
    transform.OffsetY + ny * transform.Destination.Height);
```

### 数据驱动骨架拓扑

点数不匹配则**跳过绘制，不猜**。`KeypointConfidenceFloor=0.35`（含 NaN 显式判掉）、
`BoxConfidenceFloor=0.25`。

### AI 模式四态与切换链路

`ai-off` / `ai-y` / `ai-y-pose` / `ai-hand`，服务端默认 `DefaultAIMode = ai-y`。

```
desktop → POST /api/cameras/{id}/aimode → video-server 落库
        → agent 轮询 GET → 运行时换模型（无反向推送）
```

**陈旧帧抑制**：agent 在模式切换后仍可能吐出上一种模式的帧（服务端有意原样透传
`ai_mode`，由消费端判断）。若帧的 `ai_mode` 与当前选中模式不符，丢弃不画，
否则切换瞬间会看到"旧模式的框"闪一下。

**语义注意**：`ai-off` 只是「UI 不再绘制」，agent 仍持有已加载的模型
（实测状态栏能看到 `AI: ai-y-pose 运行中 29.7fps` 而下拉框是 `ai-off`）。

**验收**：`--overlaytest` **18/18 PASS + failures=0**，含像素级断言
（框四边、框外背景、关键点、点数不匹配跳过骨架、参考分辨率 640×360 → 显示 1280×720
的归一化映射、ai-off 不绘制）。

### ⚠ 不能用 `Process.MainWindowHandle`（返回的是弹出控件）

**症状**：想抓主窗口，结果拿到 704×189 的 ComboBox 弹出列表。

**根因**：`MainWindowHandle` 是「最近活跃顶层窗口」的启发式。
下拉列表弹出时它返回的是那个弹出列表。

**修正**：改用 `EnumWindows` 枚举该进程全部可见顶层窗口，
取**面积最大**的那个——主窗口一定比任何弹出控件大。

**配套**：`MainForm(string? autoSelectKeyword)` + `--select-source <关键字>`
让 GUI 首次填充下拉框后自动选中匹配项，使无人值守截图能覆盖非默认路径
（如网络相机）。
