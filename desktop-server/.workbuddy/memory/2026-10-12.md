# 2026-10-12 — desktop-server 架构变更：本端即视频服务器

## 背景

用户明确指示：「desktop-server 作为网络视频服务器时，设计上要和 video-server 无关，
直接接收 carmera-agent 的视频流并显示」。

这推翻了此前"desktop-server 作客户端去连 video-server REST API"的设计。

```
改前：agent ─推流→ video-server(MediaMTX) ─REST→ desktop-server ─拉RTSP→ video-server
改后：agent ─推流→ desktop-server(自托管 MediaMTX) → 本地直拉显示
                  └─ POST /api/metadata → 本地叠加
```

用户三项决策：
- RTSP 接收：**内嵌托管 MediaMTX**
- metadata 范围：**完整实现两个端点**（POST /api/metadata + GET/POST aimode）
- 旧代码：**移除，只保留直连 agent**
- 端口：metadata 定 **8099**，Mediamtx 副本放 `desktop-server/mediamtx/`

## 新增代码

| 文件 | 作用 |
|---|---|
| `Server/MediaMtxConfig.cs` | `MediaMtxOptions` record + YAML 渲染/写入（UTF-8 无 BOM，MediaMTX 不认 BOM） |
| `Server/MediaMtxHost.cs` | 子进程托管：二进制查找（程序目录→仓库 mediamtx/→PATH）、等控制 API 就绪、`ListPaths()`、Kill(entireProcessTree) + 删临时 YAML |
| `Server/MetadataModels.cs` | wire 协议 DTO，逐字段对照 `metadata_encoder.cpp` |
| `Server/MetadataServer.cs` | HttpListener 服务端（:8099），204/400 契约 |
| `Server/ServerHost.cs` | 总编排：拉起两个子系统 + 1s 轮询 MediaMTX 路径 + 合并成 SourceItem |
| `ServerProbe.cs` | `--servertest` 端到端验收探针 |

删除：`Network/NetworkCameraClient.cs`、`Network/ApiModels.cs`、`NetworkProbe.cs`、整个 `Network/` 目录。

## 关键设计点

- **agent 零配置对接**：agent 从 `metadata.server_url` 去掉 `/api/metadata` 后缀自动推导
  aimode base（`stream_controller.cpp::derive_aimode_base`），所以只需指一个 --metadata-url。
- **两条独立通道**：视频走 RTP(:8554)、AI 走 HTTP(:8099)，可单独缺失，不互相覆盖。
  `VideoOnline` 与 `LastStatus` 分别记录，合并成一条 UI 条目（"AI 活着但视频断了"可见）。
- **视频在线才 IsOnline**：避免默认选中一个点开必然黑屏的条目。
- **AiMetadataPoller 改为进程内轮询**：metadata 就在本进程，再发 HTTP 给自己只是绕 loopback。
  保留 150ms 定时 + frame_id 去重，时序行为与改造前一致（验收判据不用重写）。
- **HttpListener 前缀区分 Host**：`127.0.0.1` 与 `localhost` 两个前缀都要注册。
- **端口**：8554(agent 默认) / 8099(metadata，用户指定) / 9997(控制 API) / 8889(WebRTC) / 8888(HLS)。
  8080 被 ApplicationWebServer 占、8081 被 video-server 占（实测）。

## 修复 1（真 bug）：直播源被时间戳节流吃掉了所有帧

**症状**：选中 `[服务器]` 网络相机后，状态栏显示「播放中」、日志有
`[播放] 开始，后端=Hardware 硬解尝试=True`，但**画布永远停在「未选择视频源」占位符**，
且**没有任何错误、没有 `解码结束`**。

**根因**：`PlayerController.ThrottleByTimestamp` 默认 `true`，而 `MainForm.StartPlayer`
从未按源类型设置它。对 RTSP 直播源，`DecodeLoop` 里：

```csharp
double expectedMs = presented * frameIntervalMs;   // presented=0 → 0
double actualMs   = clock.Elapsed.TotalMilliseconds; // 握手+等关键帧，早已远超一帧
double waitMs     = expectedMs - actualMs;          // 大负数
else if (waitMs < -200) { frame.Dispose(); presented++; continue; }  // 每帧都被丢！
```

首帧等待远大于一帧间隔 → `waitMs < -200` 恒成立 → **每一帧都被判「落后太多」丢弃**，
`RaiseFrameReady` 永不触发。线程阻塞在 `DecodeNextFrame()` 等下一帧，故连
`解码结束` 都不打印 —— 症状极具误导性。

**修法**：`MainForm.StartPlayer` 在 `_player.Play()` 之前加
```csharp
_player.ThrottleByTimestamp = item.Kind != SourceKind.NetworkCamera;
```
本地文件仍保留节流（避免全速解码后瞬间丢帧）。

**教训**：状态栏「播放中」只反映 `IsPlaying`，**不代表有帧**。
判断"真的在渲染"必须看 `VideoCanvas.PresentedFrames` 或截图。

## 修复 2（取证辅助）：`--select-source` 只尝试一次会静默落空

**症状**：用 `--select-source <kw>` 无人值守截图时，日志出现
`[取证] 未找到匹配「…」的源，保持默认选择`，截到的是默认源。

**两个原因**：
1. **只尝试一次**。agent 推流的网络相机往往在窗口 Shown 之后才被 MediaMTX 认出来，
   而 `TryAutoSelect` 只在 `OnFirstShown` 跑一遍。
2. **没有先刷新**。`_sourceCombo.Items` 靠 `CamerasChanged` 事件重建；
   重试若不先 `RefreshSources` 就永远看不到新条目。

**修法**：`OnFirstShown` 改为起一个 1s 间隔的 `System.Windows.Forms.Timer`，
**每次 Tick 先 `RefreshSources(autoPlay:false)` 再 `TryAutoSelect`**，
命中或 20 次后停表。`TryAutoSelect` 返回值改为 `bool` 供调用方判断。

## 踩坑：`.bat` 里的中文命令行参数会被 cmd 按 GBK 误读

`start "" app.exe --select-source "[服务器]"` 传给进程的已经是
**`[鏈嶅姟鍣╙`**（UTF-8 字节被 GBK 解释）。日志实证。

**修法**：取证脚本里**只用 ASCII 关键字匹配**（如 `e2e-ai-01`），
不要在这类参数里放中文。

## 踩坑：Git Bash 的 `timeout` 遮蔽 timeout.exe

`.bat` 里 `timeout /t 5` 在 Bash 工具调用下变成 Unix `timeout`，报
`invalid time interval '鈥�/t鈥�'` 且**不延时**（静默降级为空操作）。
**修法**：用 `ping -n 5 127.0.0.1 >nul` 代替。这与 §2 的 PATH 遮蔽同族。

## 踩坑：`--guicapture` 要么抓已存在的窗口，要么另起一个

`--guicapture` 本身也是 `VisionFlow.Desktop.exe`，直接调用会**新起一个进程**并抓它
（PID 与正在播放的那个不同 → 抓到的是刚启动的空界面）。
**必须加 `--process VisionFlow.Desktop`** 才会去找**已经在跑**的那个同名进程窗口。

## 踩坑：CS0160 catch 类型冗余

`HttpListenerException : Win32Exception : ExternalException : SystemException`，
而 `InvalidOperationException` / `ObjectDisposedException` 同样是 `SystemException` 派生，
所以第一个 catch 已覆盖后两者 → CS0160。

修法：合并为 `catch (HttpListenerException)` + `catch (Exception)`。
（若要保留具体类型，更派生的必须写在更前面。）

## 踩坑（高价值）：**是我自己的取证方法错了** —— `/tmp` 路径没落文件

**曾被误判为**："`.bat` 用 LF 行尾会让 `call :label` 重复执行"（阶段 7/8/9 各跑 7 次）。
**该结论已被本轮实测推翻，是错误归因。**

**真实症状**：日志里阶段 1–6 各 1 次，阶段 7/8/9 各 7 次，`Result:` 行有 7 条且
PASS 逐次累加（31→46→60→73→85→96→125）。

**真实根因**：我的取证命令是
```bash
cmd //c "run_tests.bat < nul > /tmp/vf_final.log 2>&1"; grep ... /tmp/vf_final.log
```
**cmd.exe 不认 MSYS 的 `/tmp` 路径，重定向根本没生效**（输出落到别处/为空），
而我 `grep` 到的 `/tmp/vf_final.log` 是**此前多次单独调试运行留下的旧文件**——
里面叠着我历史上 7 次不同运行的 RESULT 行。我以为在看"一次运行"，实际在看"7 次运行的堆积"。

**决定性验证**：改用 Windows 临时目录后干净重跑
```bash
cmd //c "run_tests.bat < nul > %TEMP%\vf_r1.log 2>&1"
```
结果 `stage seq: 123456789`、`Result lines: ['Result: PASS=50 FAIL=0 SKIP=1']` ——
**每个阶段恰好一次，7× 重复不存在**。脚本从来没坏过。

**排除掉的伪假设**（都做了受控最小复现，全部正常）：
- `call :label` 写在 `( )` 块内 → 复现正常
- `goto` 从 `if ( )` 块内跳出 → 复现正常
- 文件 > 8192 字节触发缓冲区边界 → 复现正常（8474 字节仍正常）
- 行尾：实测文件 `裸LF=0 裸CR=0 控制字节=0`，**字节完全干净**

**保留的正确实践**（与根因无关，但该做）：
- `.bat` 统一 CRLF + `.gitattributes`（`*.bat text eol=crlf`）——防止外部工具/编辑器
  重写行尾引入真实问题，属防御性措施，不是本 bug 的原因。
- 独立 stage 日志 `SLOG` 确实修掉了尾部 3 个假 FAIL（共享 `%LOG%` 的 flush 竞争），
  这条修复是**真实且必要**的。

**教训（与本环境铁律 2 同源）**：
`/tmp/*` 在 cmd 重定向下**不落文件**。凡是要让 cmd.exe 写的路径，
必须给 **Windows 路径**（`%TEMP%` 或绝对路径）。
看到"不可能的症状"时，**先怀疑取证工具本身**，再怀疑被测对象。

## 踩坑：批处理里 `call :label` 确实不能写在 `( )` 块内

虽然阶段 5/8/9 这么写一直"看着正常"（PASS 有累加），但 stage 6 首次这么写时报
`系统找不到指定的批处理标签 - Check`。稳妥做法是一律用顶层 `call` + `goto :label`
跳过，不要放进 `( )` 块。

## 踩坑：Git Bash 里 `find` 是 Unix 版

`find /c "X" file` 在 Bash 工具里跑的是 Git 的 `find`，会去遍历整个 `/c/` 文件系统
（输出 130MB 目录列表）。要统计行数用 Python 或 `findstr /C:`（走 cmd）。

## 工具链备注

- `Timer` 在启用 ImplicitUsings + WinForms 的项目里歧义（CS0104），
  须写 `System.Threading.Timer`。
- 探针的机器可读输出用**显式传入的 ASCII key**：`CHK <key>=ok`。
  不要从检查项名字自动派生 slug —— 中文名会派生出空串，
  多个检查项撞成同一个 `CHK =ok`，验收变成"看着全绿其实什么都没验"。
- `run_tests.bat` 的 pause 让 Bash 工具超时被 SIGTERM：
  用 `cmd //c "run_tests.bat < nul > log 2>&1"` 喂空 stdin。

# 任务 15 收尾：AI 模式"无人操作却自己变了"的根因（已修复）

## 症状

联调时 agent 日志出现**没有任何人请求过**的模式切换：

```
15:40:40.929  [AI] model switched -> mode=pose (models/yolo11n-pose.onnx)   ← POST ai-y-pose ✅
15:40:49.597  [AI] model switched -> mode=hand (models/palm_detection_...onnx)  ← ⚠️ 无人请求
15:40:56.089  [AI] model switched -> mode=detect (models/yolo11n.onnx)      ← POST ai-y ✅
```

伴随现象：GUI 下拉框显示的 AI 模式与实际渲染的叠加不一致。

## 定位过程（关键：先给两端都装"谁改了它"的取证）

1. 先排除 agent 自切换：`AIPipeline::request_mode()` 的**唯一调用点**是
   `stream_controller.cpp::aimode_poll_loop()`，而它只把 GET 回来的 mode 往下发。
   ⇒ agent 不会自己换模式。
2. 再排除本端 poller：`AiMetadataPoller.PollLoop` 只调 `GetOverlayState()`，纯读。
3. 打印**服务端每一个 aimode GET/POST**（临时 Diag，写 `%VF_AIMODE_DIAG%`）。
   结果决定性：
   ```
   15:46:44.560 GET -> ai-y
   15:46:48.905 GET -> ai-off      ← 值被改了，但**全程只有 2 次 POST，且都是我发的**
   ...
   15:47:06.644 POST -> ai-y-pose
   15:47:27.609 POST -> ai-y
   ```
   ⇒ 写入没走 HTTP ⇒ 是**进程内**写的。
4. `grep DesiredAiMode` 只有两个写点：`MetadataServer.cs:411`（POST 处理器，会打日志）
   与 `ServerHost.cs:292`（`SetAiMode`，**进程内直写，不经过 HTTP**）。
   POST 没记录 ⇒ 必然是 `ServerHost.SetAiMode()` 被调用。

## 根因

`MainForm.UpdateAiModeAvailability()` 做"UI 回填"时直接给下拉框赋值：

```csharp
if (_aiModeCombo.SelectedIndex < 0 && _aiModeCombo.Items.Count > 0)
    _aiModeCombo.SelectedIndex = 0;      // ← 0 == ai-off
```

`SelectedIndex` 变化会冒泡到 `OnAiModeChanged`，而该方法**只检查
`_suppressAiModeEvent`，不检查 `_populating`**，于是一次纯 UI 回填被当成
"用户点了 ai-off"，真下发给 agent：

`切换源 → SelectedIndex(-1→0) → OnAiModeChanged → ServerHost.SetAiMode(id,"ai-off")
→ DesiredAiMode="ai-off" → agent 2s 后轮询读到 ai-off`

时序也对得上：agent 的相机源在窗口 Shown 之后才被 MediaMTX 认出来，
重试定时器在 15:46:48 才选中它 → `StartSource` → `UpdateAiModeAvailability` → 此刻
`SelectedIndex` 是 -1（先前自动选中本地摄像头时被清过）→ 置 0 → 下发 ai-off。

**为什么第一轮看到的是 `hand` 而不是 `ai-off`**：同一 bug，只是当时下拉框的
选中项恰好是 index 3（`ai-hand`，来自更早一次实验遗留的 `DesiredAiMode`），
所以"被当作用户命令"的是那一条。**同一个缺陷，不同的取值**——这也解释了
为什么它看起来像"随机的、无人请求的切换"。

## 修复

1. 新增 `SetAiModeComboIndex(int)`：程序化设置选中项时用
   `_suppressAiModeEvent` 包住，**UI 回填不再产生下发副作用**。
2. `UpdateAiModeAvailability` 的两处赋值（`-1` 与 `0`）改走该方法。
3. `SelectAiModeInCombo` 原本手写 suppress，一并改走该方法（去重）。
4. 语义边界保持不变：**用户手动选 `ai-off` 仍然会下发**
   （这是 video-server 既有契约：`ai-off` 是合法可存模式，agent 有意忽略它、
   只让 Web/UI 停止绘制——见 `video-server/internal/metadata/model.go:36,49`，
   `DefaultAIMode = AIModeDetect = "ai-y"`，与本端 `DefaultAiMode` 一致）。

...

15:52:16.411 GET -> ai-y-pose
...

15:52:38.280 GET -> ai-y

## 已知遗留（非缺陷，记录备查）

- GUI 只在 `StartAiPolling()` 时**读一次**服务端模式。若通过 HTTP 外部改模式，
  下拉框不会跟着变（叠加绘制本身是按帧里的 `ai_mode` 走，所以画面是对的）。
  当前 GUI 是模式的主控方，外部 POST 只用于自动化验证，故不做轮询同步。

## 工具链备注（本轮新增）

- **诊断写入点不能只装在 HTTP 处理器上**：本 bug 的写入走的是进程内
  `ServerHost.SetAiMode`，任何"打印 POST 请求"的探针都抓不到。
  给"值被谁改了"取证时，要装在**字段的写点**，而不是请求入口。
- 构建输出路径有两套，别混：`dotnet build -c Debug` → `bin\Debug\...`
  （`build_oneclick.bat` / `run_tests.bat` 用的就是这条）；
  若额外加 `-p:Platform=x64` 会落到 **`bin\x64\Debug\...`**，
  于是"我明明重建了"但脚本跑的是另一份旧 exe。**判据是同名文件的时间戳**。
- 重建前必须确认 exe 没被占用：占用时报 `MSB3026/MSB3027`（重试 10 次后失败），
  症状像"编译错误"其实是**进程锁文件**。
