# 解码路径性能剖析报告

> 探针：`VisionFlow.Desktop.exe --decodebench <输入> [--soft] [--frames N]`
> 环境：Intel UHD Graphics 630 / 12 逻辑核心 / Windows
> 素材：`testsrc2` 合成片，H264，3840×2160，30fps，20Mbps

## 一、测量方法的关键点

**FFmpeg 解码是异步的**：真正的解码工作发生在 `avcodec_send_packet()` 内部
（一次 send 可能产出 0~N 帧），而 `avcodec_receive_frame()` 通常只是把已解好的帧
取出来，近乎零成本。

**踩坑记录**：最初只对 `receive_frame` 计时，得到「4K 软解 0.01 ms/帧」这种
荒谬数字——比硬解还"快"100 倍。正确做法是把 **send 与 receive 计入同一段**。

```
错误：tDecode 只包 receive_frame → 软解 0.01 ms/帧（假）
正确：tDecode 包 send_packet + receive_frame → 软解 5.89 ms/帧（真）
```

## 二、实测数据（90 帧，4K H264 20Mbps）

| 环节 | 硬解 | 软解 | 说明 |
|---|---|---|---|
| 解码 | **0.97 ms/帧** | 5.89 ms/帧 | 硬解快 **6.1×** |
| hwframe 搬运 | 10.14 ms/帧 | — | 硬解特有开销（显存→内存） |
| 色彩转换 NV12→BGRA | 14.80 ms/帧 | 8.02 ms/帧 | 两者都有，硬解侧更贵 |
| **合计** | **25.9 ms/帧** | **13.9 ms/帧** | 硬解反而慢 **1.9×** |

## 三、结论（必须如实记录，不粉饰）

1. **硬解本身完全有效**：解码环节 6.1× 提速，机制正确、回退路径正确。

2. **但在本架构下硬解是净负优化**，原因是硬解引入了两笔额外成本：
   - `av_hwframe_transfer_data` 把帧从显存搬回系统内存：10.14 ms/帧
   - 硬解产出的 NV12 在 `sws_scale` 转 BGRA 时更贵：14.80 vs 8.02 ms/帧

3. **根本矛盾**：GDI+ 只能吃系统内存里的位图，所以"解码在 GPU 完成"这个优势
   被"必须搬回 CPU 才能显示"吃掉了，还要额外付一次搬运成本。

4. **正确方向（尚未实现，需单独立项）**：
   - 渲染层直接消费硬解纹理（D3D11 纹理 → D3DImage/交换链），
     同时消掉 transfer 与 sws 两笔开销。WinForms 下需 `D3DImage` 或
     子窗口托管 D3D11 交换链。这是唯一的根本解。
   - ~~换更快的 sws 算法~~ —— 已实测排除，见下节。
   - ~~给 sws 开多线程~~ —— 已实测排除，见下节。

5. **当前阶段取舍**：需求 1 明确要求"基于 ffmpeg 硬件解码，硬件不支持自动切软件"。
   机制已按需求实现并验证通过。**性能优化不在本阶段范围**，
   但我不会假装硬解更快——先记录事实，后续阶段若做实时 4K 再优化渲染管线。

6. **已做的实际改进**：把 `sws_scale` 的 flag 从 `SWS_BILINEAR` 改为 `SWS_FAST_BILINEAR`。
   收益很小（10.92→10.71 ms/帧，约 2%），因为同尺寸转换的瓶颈不在算法。
   保留这个改动是因为它语义上更贴切（我们不做缩放），但**不宣称它解决了性能问题**。

## 五、色彩转换基准（`--swsbench`，独立验证）

为了确认「NV12→BGRA 这一步还有没有优化空间」，单独构造固定 NV12 4K 帧测纯转换：

| 配置 | 4K 单帧耗时 |
|---|---|
| BILINEAR（原启用） | 10.92 ms |
| FAST_BILINEAR | 10.71 ms |
| POINT | 10.69 ms |
| BICUBIC | 14.18 ms |
| FAST_BILINEAR + threads=2 | 10.63 ms |
| FAST_BILINEAR + threads=4 | 10.74 ms |
| FAST_BILINEAR + threads=12 | 10.82 ms |

**结论：算法与线程数对结果几乎无影响（差异 <3%，除 BICUBIC 慢 33%）。**

**判定：这一步是内存带宽受限，不是计算受限。** 4K BGRA 单帧 33MB，
读写各一次就是 66MB 的内存流量，10.7ms 对应约 6.2 GB/s —— 已在单通道
内存带宽的合理量级内。换算法、加线程都不可能突破物理带宽。

**唯一出路是消除这次转换本身**（渲染层直接消费 GPU 纹理），
而不是优化它。这也解释了为什么上面硬解总耗时反而更高：
硬解省下的是「计算」（解码 5.89→0.97 ms），
而额外付出的是「内存搬运」（transfer + 更贵的 sws），
在带宽受限的环节上，硬解的设计假设（算力是瓶颈）不成立。

## 四、补充观察

- 720p 场景两者差距很小（188 vs 218 fps），因为解码本身不是瓶颈。
- 硬解的价值随分辨率和码率上升而放大；搬运/转换成本同样随分辨率上升，
  当前架构下后者增长更快，所以**分辨率越高硬解劣势越明显**。
- 这恰好说明：**要不要硬解，取决于渲染管线能不能直接吃 GPU 纹理**，
  而不是取决于解码器本身。
