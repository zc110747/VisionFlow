### 教训（已升级到全局 playbook §11 / §7.4）

1. **夹具必须无损。** JPEG 下 stb_image 与 libjpeg-turbo 解码同一图：
   584177/614400 像素一致、最大差 3 LSB、16919 像素差 >1 → 残差被抬到 0.43 px
   （真实移植误差只有 0.0017 px）。噪声比信号大 250 倍，**恰好掩盖要抓的亚像素 bug**。
   换 PNG 后两侧逐字节一致，残差立刻掉到亚毫像素。
2. **基准脚本自己会错。** 官方 `_preprocess` 的 `pad_bias[0]=left / [1]=top`
   藏在 `if` 分支里，誊抄时漏掉 → 基准里每个框偏移 +160 px、选到了另一只手
   （0.70 vs 0.99），看起来像"网络选错了手"。**差分对不上先怀疑基准**，
   并用中间产物（掌心框 / anchor index）逐级定位分叉点。
3. **锚点表的参考副本必须独立誊抄**，不能用被测公式生成，否则是循环论证。
4. **`cmd.exe` 中转被沙箱拒**（Bash 与 PowerShell 两侧都拒），且
   `cmd.exe //c "x.bat"` 在 Git Bash 下会**静默空跑并返回 exit 0**。
   跑 .bat 只有 `./x.bat --no-pause < /dev/null` 一条路；
   要精确控 target / grep 零警告就用手工 MSVC env，
   **注意 Debug 首次配置需要 SDK 的 `rc.exe`/`mt.exe`**（否则报 "compiler broken"，与代码无关）。

## ✅ 画面朝向定案：摄像头滚转 90°，修正 = 顺时针

### 结论

**真实世界的"上"指向画面左侧** ⇒ 修正 = **顺时针 90°**：

| 项 | 值 |
|---|---|
| GStreamer | `videoflip video-direction=90r`（`method=clockwise` 已 deprecated） |
| ffmpeg | `transpose=1` |
| 实测输出 | 1280×720 **→ 720×1280** 竖幅 |
| 插入位置 | **caps 之后、tee 之前** |

### 过程（两条被否掉的路，值得记）

1. **第一次肉眼判读是错的。** 我一度从"人脸朝向"推出"上是右"，与"灯板在左"矛盾。
   根因：raw 帧人脸只有 ~150 px 且整体侧躺，那个尺度判上下不可靠。
   **改法：放大裁脸**（`crop=700:460:350:120` + 2× 最近邻）→ 发际在左、下巴在右；
   再把 ±90° **两种旋转都渲染出来**：顺时针得正立人脸，逆时针人头朝下 ⇒ 排除。
2. **差点把 DirectShow 当设备行为。** 第一帧是 `ffmpeg -f dshow` 抓的，
   而 agent 用的是 `mfvideosrc`（Media Foundation）—— **两条不同路径**，
   MF 会应用 UVC 的 roll 属性。改用 `gst-launch-1.0 mfvideosrc ...` 重抓，
   两条路径结论一致，才敢定案。

### 顺带查出的真实语义缺陷

`hand_map_coordinates()`（`hand_analyzer.cpp:147` 起）**硬假设画面正立**：
`x = cx/fw`（X+ 右）、`z = (fh-cy)/fh`（Z+ 上），只有 `invert_x/y/z` 三个**符号翻转**。

### 为什么"放行 `ai-hand`"是硬前提（**实测因果链**）

agent 带 `--ai-mode hand` 启动 → `[HAND] ready: mode=hand(21kpt)` →
**1 秒后** `[AI] model switched -> mode=detect (models/yolo11n.onnx)`。

根因：agent 的 aimode 轮询器读服务端存的模式，而 DB 里是 `ai-y`，
且 `ValidAIMode()` 拒收 `ai-hand` ⇒ **服务端拒绝存储 → 轮询器把 agent 拽回 ai-y**。
联合运行下 hand 模式原先**根本不可能**稳定下来（`POST ai-hand` 实测 **HTTP 400**）。

### 两条设计决定（有实测依据）

1. **payload 存 agent 原字节**，不重新序列化。可被数据自证：库里是
   `"confidence":0.00` / `position":[0.0000,...]`（C++ 定点格式），
   Go 重新编码会写 `0` / `[0,0,0]`。⇒ 后续 agent 加字段，服务端不认识也不丢。
2. **会话切分是两条独立判据**：`detected=false` **无条件**结束会话；
   `gap_ms` 只管"全是 detected 的行之间隔了多久"。
   **任何 gap 都跨不过"手离开画面"** —— 否则"握住→松开→再握"会被合并成一次。

### 我在本轮犯的错（测试预期错，不是实现错）

- API 用例我写成"`gap_ms=10000` 应把两段 hold 合成 1 个会话" → **错**：
  两段之间夹着一帧 `detected=false`，gap 没机会生效。测试已改到 gap 真正生效的场景
  （两段 hold 之间**无任何行**），并把不变式钉进纯函数表（`no gap merges across a loss`）。
- `TestHandBlockSurvivesStorage` 的 landmark 期望值我**连续手算错两次**
  （先写 `19.25`、再写 z=`0`）。根因是"手推夹具算术"，改成用**夹具同一公式**生成期望值。

### 两条"我测错了方向"的教训

1. **`gap_ms` 只在往小调时生效。** 真机相邻行 ts 间隔 p50 = **128ms**（≈8fps），
   所以 `gap_ms >= 200` 全都会桥接整段 hold。我先往 **600000** 试，看到"完全没作用"
   一度以为参数坏了 —— **那是探测方向错**。实测：`30→2193`、`128→697`、`200→195`、`1000→194`。
2. **landmark 落在画面外不是缺陷。** y 有 1070 个点 > 720（814 行），x 则全部在 `[0,1280]` 内。
