## 分段算法：三个失败变体（都实测过，供以后复用）

写 `verify_hand_direction.py` 时锚点设计错了三次，每次都**在真实数据上不可见**：

1. 锚点每帧跟随 → 追掉 0.05 动作的 72%，**0 段**（会被读成"操作者没动"）；
2. 用最近 N 帧均值重新居中 → 那些帧横跨回位斜坡，锚点偏中位 **0.016 > return_band 0.012**
   ⇒ 下一段永远合不上，**把后面所有动作全吞了**；
3. 吸附但**忘了清零 settle 计数** → 此后每帧都吸附，锚点被钉在手上，峰值只有 **0.0101**。

最终设计：锚点只在"确认静止 `settle_ms`"后吸附，且**吸附后必须清零计数**。
代价：慢于 `return_band/settle_ms` 的动作会被吸进锚点而不上报（已在文档写明）。

另外加了**入画过渡跳过**：录制从"手刚入画"开始，那一瞬的位移本身就是一次
"永不回位"的运动，会把第 1 个动作吃掉。现在只在找到"连续静止窗口"后才开始找动作
（真实会话 865 上跳过了 13 帧）。

## §16 方向实验：改成"不下清库 + 实时监测"（09:23）

用户要求"一直监测，满足要求后自动切换下个步骤"，于是不再走"清库 → 手动跑分析"，
改成 `%TEMP%\vf-watch.py`：轮询录制器、实时分段、满 4 段干净动作就**自动落到裁决表**。

三个设计决定：

1. **不清库，用 `--since <ISO>` 过滤 `received_at`。** 清库会毁掉"操作者提前开始"的
   数据，而且清库前那 27 秒的静持姿态（211 帧连续 FIST、position 全幅仅 0.039）本来
   就该被排除——它是中位基准，不是动作。ISO 字符串**逐位比较**即可当时间谓词用
   （同格式、同长度前缀），不需要解析。
2. **触发判据必须严**：子序列匹配期望轴向 + 主轴领先次轴 ≥1.5 倍才算数。
   宁可超时也不早报——早报等于用不足以支撑结论的证据给出自信结论。超时路径仍打印
   诊断表并**显式标注"这不是裁决"**。
3. 会话按 index 顺序拼接（会话边界 = 手离开画面，不等于操作者停顿），只有尾部 3 个
   会话每轮重取，其余走缓存。

**新踩到的静默坑（高价值）**：同一条消息里对**同一个文件**发多个 `Edit`，只有**一个**
会落盘（实测 3 个里 2 个丢失，3 个都报"成功"）。`match_axes()` 加了 `ratio` 参数但调用点
没改，运行才炸出 `TypeError: missing 1 required positional argument`。
⇒ **同文件的多处修改必须串行，一次一个 `Edit`，改完 `grep` 核对。**
判据是"改完后 grep 能不能同时看到所有改动"，不是 Edit 的返回文案。

## §16 方向实验：一个决定性的负面结论（用户提出"摄像头是斜的、三轴联动"后被证实）

用户观察：**摄像头整体倾斜、且并非正对运动平面，动作下 x/y/z 大部分情况联动**。数据完全
支持，而且比他说的更严重。归档 run1：1160 帧（09:23:17Z 之后），`spec16-run1-raw.json`。

**结构根源**（`hand_analyzer.cpp:141-201`）：三个逻辑轴全部来自**同一个检测框**
`x=(x1+x2)/2/fw`、`z=(fh-(y1+y2)/2)/fh`、`y=sqrt(bw*bh)/fh`。一个 4 自由度矩形 → 3 个输出，
**天生不独立**。

**实测耦合**（同一帧集、无子集错配）：

| 量 | 值 |
|---|---|
| `corr(position.Y, position.Z)` | **+0.837** |
| `corr(position.Y, 手部质心y)` | −0.555 |
| `corr(手部尺寸, 手部质心y)` | −0.492（只用关键点，纯几何） |
| `corr(position.X, 手部质心x)` | +0.988（R²=0.977，X 几乎就是图像横坐标） |
| PCA 主方向 | #1 73.4% `[-0.11,+0.84,+0.54]`（上举且变近）、#2 21.3% `[+0.99,+0.15,-0.04]`（纯横向）、#3 5.3% |
| 8 段动作中 `dY` 与 `dZ` 同号 | **8/8** |

⇒ **观测到的运动自由度实际只有 2 维**（73.4%+21.3% = 94.7% 落在一个 2 平面上）。

**来源分解（我自己的脚本曾给出错误结论，已订正）**：
换用关键点导出的尺度**并不能**把耦合砍半。正确对比是同一对量：
`corr(Y,Z)=+0.837` → 在 `lmspan`(刚性骨长) 上 `corr(lmspan,Z)=+0.782`，`lmsize` 上 `+0.734`。
即 R² 0.70 → 0.54~0.61，**只降约 15%**。
（错因：拿 `corr(Y,Z)` 与 `corr(lmsize, lmy)` 比 —— **不是同一对量**，分母/配对都不同。）
⇒ **耦合主体来自倾斜透视本身，配置或公式都改不掉。**

**结论（写进 §16 的核心）**：本机挂载下 `position.y` **不能当独立的"前后"轴**。
`invert_x/y/z` 与 `depth_source` 都无法修复它。真正的修法是**机械调整摄像头朝向**，让光轴
垂直于手的运动平面；验证判据就是重跑本分析，看 `corr(尺寸, 图像纵坐标)` 是否趋近 0。

**连带影响**：HUD 的 `F/B`（前进/后退）运动标签在本挂载下不可靠；X/Z 可靠（X 近乎独立，
Z 与图像纵坐标 corr −0.825）。

**录制数据的字段缺口**：`/hand/sessions/{idx}` 的行**只有 `hand` 块**，没有 `objects`、也没有
`video_width/height`（实时 `/metadata` 才有）。所以 `position` 的框**无法从归档反算**；
但 21 个关键点都在，可用它们做纯几何分析（本次就是这么做的）。
另：`hand.detected=false` 时 `position=[0,0,0]` —— 分析/前端必须按 `detected` 门控，
否则 0 值会被当成一次巨大位移。
