## build_oneclick.bat / start-camera-agent.bat 真实修复（阶段 4，已实测通过）

### build_oneclick.bat（之前报错 "此时不应有 ." RC=255）
- 根因1：`echo [ERROR] Visual Studio not found (looked in '%VSPATH%').` —— 括号内 echo 串里的 `)` 提前关掉
  `if not exist (...)` 块（cmd 不把引号内 `)` 当字面量），导致后面 `'.` 成为 "unexpected"，整文件解析失败。
  即使该 `if` 分支运行时被跳过，解析期仍报错。改法：echo 串去掉 `()`（改成 `- looked in %VSPATH%`）。

  cmake 把整行当成 -S 参数 → "source directory does not exist"。改法：`if "%ROOT:~-1%"=="\" set ROOT=%ROOT:~0,-1%` 去尾斜杠；
  并修 `set BUILD=%ROOT%\build-msvc` / `set EXE=%ROOT%\build-msvc\...`（去尾斜杠后必须显式补 `\`，否则拼成 `carmera-agentbuild-msvc` 兄弟目录）。

## 端到端延迟评估与 camera-agent 内部优化（阶段 5）

### 现象
流程跑通，但"视频动作延时大概超过 1s"。用户要求先评估卡点，mediamtx / ffplay 暂不动。

### 卡点定位（camera-agent 内部可控）
链路：`mfvideosrc → videoconvert → caps → encoder → h264parse → rtspclientsink`
1. **编码未开低延迟（最大头）**：`encoder_element()` 只对 x264enc 加 `tune=zerolatency`；
   但 `pick_encoder()` 实际优先返回 **nvh264enc**，走 hw 分支只设 `bitrate`（无 zerolatency/tune/bframes/lookahead）。
   NVENC 默认 B 帧重排 + lookahead → 300ms~1s+。
2. **整链无 queue**：采集→转码→编码→parse→sink 同线程串行，编码慢阻塞采集、帧无法解耦。
3. **rtspclientsink 缓冲**：未设 `latency`/`rtx-time`，推送端默认缓冲。

### 用 gst-inspect 确认的合法属性（关键，避免瞎改）
- `nvh264enc`：`tune`(2=low-latency,3=ultra-low-latency)、`zerolatency`(true=禁重排)、`bframes`、`rc-lookahead`、`repeat-sequence-header`、`qos`。
- `rtspclientsink`：`latency`(ms 缓冲)、`rtx-time`(重传缓冲，0=禁用)、`udp-buffer-size`。
- `mfvideosrc`：无延迟相关属性（采集端固有，240×240@8fps 帧间隔 125ms）。

### 改动（src/pipeline/video_pipeline_gst.cpp）
- `encoder_element()` 按 enc 名分类加低延迟：
  - nv*：`tune=ultra-low-latency zerolatency=true bframes=0 rc-lookahead=0 repeat-sequence-header=true`
  - mfx*：`tune=low-latency bframes=0 rc-lookahead=0 repeat-sequence-header=true`
  - x264：`tune=zerolatency speed-preset=veryfast bframes=0`（原只缺 bframes=0）
  - 其他 hw：至少 `bframes=0`
- `build()` 的 desc 在每段间插 `queue max-size-buffers=2 max-size-bytes=0 max-size-time=0`（最多 2 帧缓冲，防堆积）；
  rtspclientsink 加 `latency=0 rtx-time=0`。

### 验收
- `./build_oneclick.bat`：增量重编，RC=0，**0 warning / 0 error**，exe 更新（315904B）。
- 离线 link 验证（gst-launch，videotestsrc→fakesink 替换摄像头/RTSP）：RC=0，整链 link 成功、NVENC 走 CUDA、30 帧正常跑完，
  证明 queue + nvh264enc 低延迟属性 + sink latency=0/rtx-time=0 全部合法可跑。
- 真机端到端延迟需用户在有摄像头机器上复测（沙箱无摄像头，且 mediamtx/ffplay 未动，其默认缓冲仍是延迟大头）。

### 结论 / 提示
- 上述改完预计能砍掉 camera-agent 内部大部分（数百 ms~1s）编码+缓冲延迟。
- 若真机复测仍 >1s，大头在外部：mediamtx 转发缓冲 + ffplay 的 `rtspclientsink`/`rtspsrc` 默认 `latency=2000ms`（播放端），按用户要求暂未动。

## mediamtx / ffplay 配置选项评估与优化（阶段 6）

### 用户要求
camera-agent 已优化，现在看 mediamtx/ffplay 的配置选项继续压延迟。

### 评估结论
- **mediamtx 本质是 RTP pass-through，自身延迟极小**，可榨的油很少。路径级可调项里与延迟相关的只有
  `rtspTransport`（auto/tcp/udp）、`record`(off 才不引磁盘缓冲)、`writeQueueSize`(默认512)、`readTimeout`(默认10s)。
- **ffplay / RTSP 订阅端才是播放侧延迟大头**：`rtspsrc` 默认启动缓冲 ~2s；原脚本只给了
  `-rtsp_transport tcp -fflags nobuffer -flags low_delay`，漏掉最大项。

### 改动
- `mediamtx.yml`：新增 `paths.all_others.rtspTransport: tcp`（强制 TCP 交织，与 rtspclientsink 已用 TCP 一致、
  确定性更好）+ `record: no`（不引磁盘缓冲）。YAML 校验通过。
- `start-camera-agent.bat` 的 ffplay 启动行扩成低延迟旗标组：
  `ffplay -rtsp_transport tcp -rtsp_flags nobuffer -fflags nobuffer -flags low_delay -probesize 32768 -analyzeduration 0 -framedrop rtsp://127.0.0.1:8554/camera01`
  - `-rtsp_flags nobuffer`：关 RTSP demuxer 启动缓冲（原缺，最大头 ~数百ms~2s）
  - `-probesize 32768` / `-analyzeduration 0`：最小化流探测/分析等待
  - `-framedrop`：落后帧丢弃保持实时
- 校验：ffplay 只给旗标不给 URL → 报 "An input file must be specified"（证明无 Unrecognized option，旗标全合法）。

### 量化预期（需真机复测）
- camera-agent 内部（阶段5）+ 本阶段 ffplay 端，端到端动作延迟应从 >1s 降到约 200~400ms 量级
  （受 240×240@8fps 帧间隔固有 125ms + 编码/网络/解码残余）。
- mediamtx 强制 TCP 不增延迟；`writeQueueSize`/`readTimeout` 暂保持默认。
- 仍残留的延迟变量：8fps 帧间隔（采集端固有，改 fps 才能变）、NVENC 编码残余、本地回环网络。

### 备注
- `keyframe_interval: 30`（默认）→ GOP 30帧@8fps≈3.75s；mediamtx 等新订阅者要等到下一 IDR 才转发首帧。
  阶段5 已加 `repeat-sequence-header=true`（流自包含），缓解 reconnect 等待；如要更快首帧可降到 15~20。

## camera-agent 内部延迟探针（阶段 7，已实现并实测）

### 用户需求
只测 camera-agent 内部延时（采集→编码→推送到 mediamtx），不动 mediamtx/ffplay。
方法：在 GStreamer 管线 3 个边界加 pad probe，按帧记录墙钟时刻相减。

### 实现（src/pipeline/video_pipeline_gst.cpp）
- 新增 `LatencyTracker` + `latency_probe_cb` + `LatencyCbCtx`；管线元素命名 `cam`/`enc`/`parse`/`sink`。
- 3 个 probe 挂在：capture=`cam.src`、encode=`enc.src`、push=`parse.src`。
  - 关键坑：`rtspclientsink` 是 **request pad（sink_%u）**，无静态 `sink` → 改用 `h264parse.src`（rtspclientsink 作为 sink 拉数据，parse.src 触发即"取到编码帧去推送"边界，等价）。
- **不用 PTS 配对，用 FIFO 顺序配对**：H264 编码器会**重打 PTS**，按 PTS key 会导致三段对不上（实测 matched=0）。
  改法：`cap_q/enc_q/push_q` 三个时间戳队列，push 时取三者队首计算 `capture->encode` / `encode->push` / `total`。
  限定 bframes=0（无重排）→ 1:1 顺序成立。队列超 1024 清空防 desync。
- 开关：`PipelineParams.measure_latency` ← `Config.measure_latency` ← CLI `--latency-probe`（默认关，不影响生产）。
- 新增 `--source <elem>` 透传（含 `videotestsrc` 合成源），`source_element()` 未知名直接透传；
  `videotestsrc` 自动加 `is-live=true`（否则非实时源不限速灌帧，破坏 FIFO 平衡）。
- `start-camera-agent.bat` 也解析 `--latency-probe` 透传给 camera-agent。

### 校验（沙箱，无摄像头，用 videotestsrc 注入）
- `./build_oneclick.bat`：6 次增量重编全 **0 warning / 0 error**。
- 端到端跑：`camera-agent --source videotestsrc --latency-probe --width 240 --height 240 --fps 8`（mediamtx 先起）。
  稳态输出（每秒一行，n≈8）：
  `[latency] capture->encode=1.0ms  encode->push=20ms  total(capture->push)=20ms (n=8)`
  首个窗口 397ms 为启动瞬态。
- **结论：camera-agent 内部端到端延时 ≈ 20ms**；用户之前观察到的总延时 >1s 不在本模块，
  由 mediamtx/ffplay/网络 + 8fps 帧间隔(125ms) 主导。真机用 `--latency-probe` 复测同上。

### 备注

## 分辨率/帧率自动协商（阶段 8，已实现并实测）

### 用户需求
camera-agent 启动是否必须指定宽高帧率？能否指定 UVC 设备后自动选合适宽高帧率？
→ 结论：当前**必填**（默认 1280×720@30，会被强写进 `video/x-raw,width=,height=,framerate=` caps）。
对原生 240×240@8fps 的 UVC 设备，强制 caps 协商失败 → 进重连循环。用户选「原生直通」方案。

### 实现
- `PipelineParams.auto_res`（video_pipeline.h）、`CameraConfig.auto_res`（config.h）、YAML `camera.auto`、CLI `--auto` 三处打通；`stream_controller` 透传 `pp_.auto_res`。
- `video_pipeline_gst.cpp` `build()`：`auto_res` 为真时**不在 videoconvert 后插 caps 过滤器**（原生直通），
  让 GStreamer 协商摄像头默认/原生格式；否则保持原强制 caps。
- 新增 `query_negotiated()`：PLAYING 后查 **`cam.src` pad 的协商 caps**（摄像头源 pad 必有固定 caps，含宽高帧率；
  编码器 sink pad 在 PLAYING 时可能只回模板 caps 而无宽高 → 改用源 pad 才可靠），解析宽高帧率存入
  `neg_w_/neg_h_/neg_fps_` 并打印 `Negotiated capture format: WxH @ Ffps`；`get_negotiated_resolution()` 虚方法
  供 `stream_controller.get_device_info()` 上报真实分辨率（值变化才重打，去重）。
- 注意：`videoconvert` 只转像素格式**不缩放**，故原生直通=摄像头给什么推什么；要固定输出尺寸需另加 `videoscale`。

### 验收
- `scripts/build-msvc.ps1 -Backend gstreamer`：增量重编 **0 warning / 0 error**，exe 更新。
- 真机 `--auto --source mfvideosrc`：日志 `Auto-resolution: not forcing caps` → `Negotiated capture format: 240x240 @ 8fps`
  → STREAMING，~8fps 稳定推流（47 帧/8s，0 dropped）。自动识别出 UVC 原生格式，无需手填 `--width/--height/--fps`。
- 反向确认：默认（非 auto）仍走强制 caps，对 240×240 设备会协商失败（预期，符合历史记录）。

## GStreamer 探测改为零硬编码（跨机器可移植）

### 症状
GStreamer 装在 `D:\software\msvc_x86_64\gstreamer`（Inno Setup 安装，扁平布局 `<root>/{bin,lib,include}`），
编译报 **找不到 `gio/gio.h`**。

### 根因
`CMakeLists.txt` 候选路径写死为 `C:/Program Files/...`、`C:/gstreamer/1.0/msvc_x86_64`、
`D:/Software/gstreamer/1.0/msvc_x86_64`，**三个都不存在**；随后静默回退到不存在的
`C:/Program Files/gstreamer/1.0/msvc_x86_64`，`find_path` 全落空 → 包含目录残缺 → `gio/gio.h` 报错。
旧代码手工拼 include 目录，漏掉 `glib-2.0` / `lib/glib-2.0/include` 就会踩坑。

### 改动
1. **`CMakeLists.txt`** 重写探测：
   - 解析顺序：`-DGSTREAMER_ROOT` → `$ENV{GSTREAMER_ROOT}` → `$ENV{GSTREAMER_1_0_ROOT_MSVC_X86_64__Plus}`
     / `..._MSVC_X86_64` / `..._X86_64`（官方安装程序变量名）→ `PATH` 里 `gst-launch-1.0`/`gst-inspect-1.0`/
     `pkg-config` 反推 → 通用默认前缀。**仓库内无任何机器路径。**
   - 同时识别两种布局（扁平 `<root>/include/...`、带版本 `<root>/1.0/msvc_x86_64/...`）；
     候选必须真实存在 `include/gstreamer-1.0/gst/gst.h` 才采纳。
   - **优先用 GStreamer 自带 `pkg-config.exe`**（`<root>/bin`，`.pc` 用 `${pcfiledir}/../..` 相对定位，
     移到哪都能用）；CMake 自动注入 `PKG_CONFIG_PATH=<root>/lib/pkgconfig`。无 pkg-config 时回退标准布局逐个校验。
   - 链接库一律 `find_library` 解析成绝对路径（对 MSVC 最稳）。
   - 新增 `gio/gio.h` 可达性自检；显式 `-DCAMERA_AGENT_BACKEND=gstreamer` 却找不到时 **FATAL_ERROR 并给修复指引**，

2. **`src/CMakeLists.txt`**：加 `VS_DEBUGGER_ENVIRONMENT` 注入 `<root>/bin` 调试 PATH（不依赖机器 PATH）。
3. **机器侧（不入仓库）**：用户级 `GSTREAMER_ROOT=D:\software\msvc_x86_64\gstreamer` + `...\bin` 追加进用户 PATH

## start-camera-agent.bat 实战排障（LRCP USB2.0 摄像头）

用户诉求：环境已装好、用 **LRCP USB2.0** UVC 摄像头，`start-camera-agent.bat` 跑起来后没画面，要求实测并修好；且**脚本不要写死路径**（工具已加进系统 PATH，直接调用）。

### 共 5 个 bug（层层暴露，必须逐条实测才能发现）

| # | 症状 | 根因 | 修法 |
|---|------|------|------|
| 1 | `[ERROR] 'mediamtx' was not found on PATH` | 脚本写死 `D:\data\agent-tools\...`，实际工具在 `E:\agent-tools\` | 删掉 `add_tool_path` 整段与三个硬编码目录，全部按裸名称调用 |
| 2 | 摄像头参数写死 `--camera 0 --width 240 --height 240 --fps 8`（为旧设备 "UVC Control" 而设，LRCP 不支持 240×240） | 参数硬编码 | 改为 `CAMERA_ID/CAMERA_AUTO/CAMERA_WIDTH/.../RTSP_PORT` 环境变量 + 命令行参数，默认 `--camera 1 --auto` |
| 3 | ffplay 窗口永远不出现（一启动即退） | `-rtsp_flags nobuffer` 是**无效参数**，`rtsp_flags` 不接受该值 → `Invalid argument` | 去掉该旗标，改用 `-max_delay 0` |
| 4 | 修好 3 后 ffplay 仍 404 退出 | agent 报 `STREAMING` 比 mediamtx 真正注册 path 早约 1 秒，ffplay 抢先 DESCRIBE → `404 Not Found` | 等 `STREAMING` → 再等 mediamtx 日志出现 `is publishing` / `stream is available`；用 `ping -n` 做可靠延时（**不用 `timeout.exe`**，它需要控制台、stdin 重定向时行为异常） |
| 5 | 整段脚本静默中止（ffplay 那步根本没执行） | **batch 括号坑**：`echo` 文本里的 `)` 提前闭合了 `if(...)else(...)` 块。两处：① 诊断提示里的 `(list devices: ...)` ② 被移进 if 块后的 `Starting ffplay (viewer)` | 块内文本一律不含括号，改用 `-` 或改写措辞 |

### 关键认知（可复用）
- **batch 括号是隐形炸弹**：`if (...) else (...)` 块内的 `echo`/文本若含 `(` 或 `)`，会提前闭合块，后续语句变成顶层或触发语法错误，表现为"脚本静默停在某行"。块内文本必须无括号（或 `^(` / `^)` 转义）。
- **`timeout.exe` 不适用于 stdout 被重定向的 bat**，用 `ping -n N 127.0.0.1 >nul` 延时（`-n 2`≈1s，`-n 4`≈3s）。
- **不要靠 grep "error/failed" 判断推流失败**：GStreamer/GIO 会打印良性告警
  `Failed to load module: ...giolibproxy.dll`，会被误判成致命错误、提前中止等待。改为只轮询 `STREAMING`，超时未出现再给排查方向。
- 判断"流已就绪"的权威信号是 **mediamtx 日志的 `is publishing`**，而非 agent 自报的 STREAMING。
